# Korea_Reconstruction

수도권(서울·경기·인천) **아파트 재건축 사업 진행 현황** 데이터. 정부·지자체가 공개한 자료만 모아 사업장 단위로 합치고, GitHub Actions가 매일 바뀐 부분만 갱신한다.

## 검색 페이지

**https://kyoungwhankim.github.io/Korea_Reconstruction/** — 단지명·별칭, 시도·시군구, 주소, 진행 단계, 용적률·건폐율·세대수·구역면적·준공연도 등 필드별 조건으로 검색. 검색 조건은 주소(URL)에 남아 그대로 공유할 수 있다. 페이지는 `docs/`에 있고 `docs/data/projects.json`을 읽는다(매일 갱신 때 함께 커밋).

## 30년 이상 노후 단지 (`complexes.py`)

재건축 사업장과 별도로, 수도권에서 준공 30년이 넘은 아파트 단지 전체(사업이 아직 없는 단지 포함)를 모은다. 페이지의 **30년 이상 노후 단지** 보기, `output/old_apartments_latest.csv`, `docs/data/apartments.json`.

- **단지의 기준은 한국부동산원 「공동주택 단지 식별정보」**(`identity.py`, 공시대상 공동주택 전수, 수도권 아파트 약 2만 단지): 단지 1개 = `COMPLEX_PK`. 이름 3개(1순위는 국토부 실거래 단지명과 같은 체계)와 옛 이름, PNU(지번), 세대·동수, 사용승인일, 그리고 필요한 단지의 **동 목록·층수**를 받는다(`state/complexes/reb.jsonl`, `reb_dongs.jsonl`; 전수는 분기, 동 목록은 하루 1,500단지씩).
  - 한 지번에 단지가 여럿일 수 있다(예: 산본동 1155-7에 '가야3주공'과 '가야주공(임대)'). 지번은 단지들의 묶음으로만 쓰고, 대지면적·용적률처럼 지번 단위인 값은 "지번 전체 값"으로 표시한다.
  - 부동산원 주소는 '경기도 수원권선구 권선동'처럼 형식이 제각각이고 인천은 개편 전 구 이름을 써서, 지역은 주소가 아니라 PNU의 법정동코드로 정하고 옛 코드는 현재 코드로 바꾼다(`bjd_canonical`).
- **실거래가**를 수도권 83개 시군구 전체에서 받아, 1996년(=올해−30) 이전 준공 단지의 거래를 남긴다 → 준공연도·전용면적별 가격. 거래는 지번 → 단지명 → **동 번호**(aptDong, 약 80% 채워짐) 순으로 단지에 붙이고, 못 가리면 "지번 공통"으로 둔다. 매매는 2006년부터의 이력, 전월세는 최근 12개월(아래 '거래 정보' 절).
- **건축물대장 총괄표제부**를 법정동(동·리 약 2,900곳)마다 나열 → 대지면적·용적률·건폐율·사용승인일(지번 단위). 분기마다 한 바퀴, 매일 100곳씩(`state/complexes/registry.jsonl`, `registry_dongs.json`). 총괄표제부 세대수는 두 배로 적힌 사례가 있어 세대수는 부동산원·K-apt 값을 우선한다.
- 사용승인일이 어디에도 없는 100세대 이상 단지는 동별 표제부로 채운다(매일 150곳).
- 이름: 'N단지'·'N차'가 든 이름을 우선 보여주고(주공6단지세종아파트), 주공 단지는 동 번호의 백 자리로 단지 번호를 추정해 별칭을 더한다(501~516동 → '가야주공5단지', 별칭 종류 `동번호 추정`). 모든 출처의 이름이 별칭이 되어 어느 이름으로든 검색된다.
- 재건축 사업장 대표 지번과 같은 지번의 단지에는 사업 단계를 붙인다.
- **K-apt**(공동주택관리정보시스템, `AptListService4` 단지 목록·`AptBasisInfoServiceV5` 기본정보): 분기마다 단지 목록, 단지별 기본정보는 한 번 받아 캐시(`state/complexes/kapt*.jsonl`) → 공식 단지명·사용승인일·세대수·동수·최고층·난방·시공사. 의무관리대상(대략 150세대 이상) 단지만 있다. 인증키가 K-apt에 등록되지 않았으면 건너뛴다.
- 준공연도는 부동산원 사용승인일 > K-apt > 실거래 건축년도 > 건축물대장 순으로 쓴다(1960년 이전 값은 오기로 보고 버림).
- 한계: 부동산원에 없는 지번(소규모 단지 등)은 지번 단위 항목으로 남는다(약 100곳). 한 단지가 여러 지번에 걸치면 지번별로 나뉠 수 있다.

- 오래된 건축물대장은 대지면적이 비어 있는 경우가 많아 대지지분은 일부 사업장만 나온다.
- 준공된 사업장의 지번에는 새 아파트가 있어 `trade_basis = 준공 후 신축`으로 구분한다. 진행 중인 사업장에서 기존 단지보다 훨씬 늦게 지어진 건물의 거래는 뺀다.
- 입주권·분양권은 신축 단지명(예: 올림픽파크포레온)과 신축 지번으로 신고돼 기존 사업장과 자동으로 맞지 않는 경우가 많다. `manual_new_names.csv`(`project_id,new_name`)에 신축 단지명을 적으면 그 이름으로 연결된다(수기 입력, 현재 둔촌주공·신반포4지구). 재개발 사업장의 입주권은 이 저장소 범위 밖이라 버린다.
- 인증키: GitHub Actions는 secret `DATA_GO_KR_KEY`(Decoding 키), 로컬은 `.env`(커밋 안 됨)에 `DATA_GO_KR_KEY=...`. 키가 없으면 보강만 건너뛴다. 요청은 초당 5건으로 제한한다(넘으면 429). 실거래 세 API는 각각 일 10,000건이며 한도 초과 응답(`returnReasonCode 22`)을 받으면 그 서비스는 그날 더 부르지 않는다.
- 실행 순서와 시간: 출처 갱신 → 건축물대장·매매 창·전월세·분양권(약 600건, 2분) → 식별정보·건축물대장 목록·K-apt(각 일 예산) → **매매 이력은 맨 마지막에 실행 시작 32분까지**만 받아, 워크플로 timeout 50분 안에 내보내기·커밋이 끝난다. 하루 두 번 실행해도 이력 호출은 상태 파일의 날짜별 합계로 8,000건을 넘지 않는다.
- 페이지 데이터(`docs/data/apartments.json`, `projects.json`)에는 숫자 요약(12개월 중위·전세가율·이력 건수 등)만 넣고, 건별 목록과 면적대별 표는 `docs/data/trades/<id>.json`에 단지별로 둔다(한 거래가 한 줄이라 diff에 새 거래만 보인다).

## 매일 갱신 (`.github/workflows/daily-update.yml`)

매일 07:30 KST에 `update_daily.py`가 실행되고, 바뀐 것이 있을 때만 커밋한다.

1. **출처 단위**: 파일 ID·파일명(probe)이 그대로면 내려받지 않는다. probe가 없는 출처는 받아서 내용 해시를 비교한다.
2. **행 단위**: 바뀐 출처만 이전 행과 비교해 추가·수정·삭제된 행을 고른다.
3. **사업장 단위**: 그 행에 연결된 사업장만 다시 계산하고 필드별 변경 이력을 남긴다.

상태(`state/`)는 정렬된 JSONL 텍스트라 커밋 diff에 바뀐 행만 보인다. 일부 출처가 실패하면 성공한 부분은 커밋하고 그 출처는 이전 데이터를 유지한다. 하루 이틀의 일시 장애(GitHub 실행기의 해외 IP를 막는 부천시·경기데이터드림 등)는 요약에 ⚠️로만 남기고, 같은 출처가 3일을 넘겨 계속 실패하면 실행을 실패(❌)로 표시한다(`state/meta.json`의 `fail_since:*`).

**부분 응답은 반영하지 않는다.** 출처가 목록의 일부만 돌려주면(해외 IP 차단, 빈 쪽 응답 등) 행이 대량으로 "삭제"된 것처럼 보이는데, 지운 행을 되살리는 비용이 훨씬 크므로 두 겹으로 막는다.
- 정보몽땅 목록은 1쪽에서 읽은 쪽 수·전체 건수와 맞지 않으면(짧은 쪽, 빈 쪽, 같은 쪽 반복) 쪽을 다시 받고, 끝내 안 맞으면 그 회차를 버린다.
- 어느 출처든 살아 있는 행의 30%가 넘게 한꺼번에 사라지는 응답은 부분 응답으로 보고 실패 처리한다(기존 행 유지, 실행은 실패 표시). 실제로 줄어든 것이면 `python update_daily.py --accept-shrink`로 한 번 반영한다.
Actions 탭 → *Daily reconstruction update* → *Run workflow*로 수동 실행할 수 있다(`force`: 모든 출처를 강제로 비교).

## 로컬 사용

```bash
pip install -r requirements.txt
python search_reconstruction.py 은마          # 어떤 이름으로든 검색 (--all: 단계별 일자)
python update_daily.py --dry-run              # 지금 갱신하면 무엇이 바뀌는지만 확인
python collect_reconstruction.py              # (검증용) 상태와 무관하게 전체를 새로 구축 → output/*_full_*.csv
python update_daily.py --migrate              # 수집 열을 늘린 뒤 1회: 새 열 때문에 생긴 변경은 이력에서 제외
python -m http.server 8000 --directory docs   # 검색 페이지 로컬 확인 → http://localhost:8000
python update_daily.py --skip-enrich          # 오픈API 보강 없이 출처만 갱신
python update_daily.py --history-budget 500   # 이번 실행의 매매 이력(2006년~) 요청 수를 제한(0이면 받지 않음)
```

`manual_aliases.csv`에 행을 추가하면 자동으로 못 묶은 같은 사업장을 합치거나, 공식 자료에 없는 통칭(예: `압구정 현대`)을 별칭으로 붙일 수 있다. 다음 실행 때 반영된다.

## 한계

- 경기 광주·양주·여주·포천·가평·양평·연천, 인천 영종·검단·옹진은 공개 데이터셋이 없다.
- 소규모재건축·리모델링은 포함하지 않는다. 안전진단 단계는 서울(정보몽땅)만 잡히고, 경기·인천은 정비구역 지정 전 단계가 공공 데이터에 없다.
- 경기도 도 데이터는 기준일이 1년 가까이 지연된 상태다(2025-09-30). 고시·뉴스 감시(3단계)로 보완할 계획.
- 경기데이터드림(data.gg.go.kr)과 부천시(www.bucheon.go.kr)는 GitHub 실행기(해외 IP)에서 간헐적으로 접속 자체가 막힌다(TCP connect timeout — 2026-10-18 실행 #7·#8은 두 출처가 모두 실패, 같은 날 #6·#9와 다음 날 정기 실행은 성공). 그날은 ⚠️로 남기고 이전 데이터를 유지하며, 14:30 KST 보조 실행이 다시 시도한다. 접속 단계에서 끊기므로 User-Agent·Accept-Language 같은 요청 헤더로는 달라지지 않고, 프록시·우회 서버는 쓰지 않는다.
- 두 출처의 공공 대체 경로는 없다(2026-10-19 확인). 공공데이터포털의 「경기도_일반 정비 사업 추진 현황」(15119846)과 「경기도_부천시_도시정비사업추진현황」(15051011)은 파일 없이 원 사이트 URL만 등록된 항목이고(제공형태 "기관자체에서 다운로드"), 둘 다 오픈API 변환(api.odcloud.kr)이 없으며("등록되지 않은 서비스"), 경기데이터드림 Open API에도 이 데이터셋은 없다. 시군이 따로 올린 파일(고양 15085975, 안양 15150142, 이천 15150059, 하남 API 15150356)은 일부 시군뿐이고 열 구성도 달라 대체가 못 된다.
- 출처가 대부분 월·분기 단위로 갱신되므로 매일 실행해도 변경이 없는 날이 많다.
- `manual_aliases.csv`의 압구정 통칭 행과 `manual_new_names.csv`의 신축 단지명은 공식 자료가 아닌 수기 입력이다.
- 매매 이력은 처음 약 3일에 걸쳐 채워지고(최신 달부터), 해가 바뀌어 노후 기준이 올라가면 다시 한 바퀴 받는다. 받을 때 거른 거래(노후 기준보다 늦게 지어진 단지)는 그때까지 이력에 없다. 거래 건축년도가 비어 있고 부동산원·건축물대장에도 없는 지번의 거래는 사업장에 연결된 경우에만 남는다.
- 전세가율은 같은 전용면적대(㎡ 반올림)의 12개월 중위끼리 비교한 값이라 거래가 적은 면적대에서는 흔들릴 수 있다.
